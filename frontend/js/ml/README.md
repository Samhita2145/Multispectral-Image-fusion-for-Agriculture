# js/ml — real models, running client-side, no backend

This folder runs **actual trained models** from `training_testing/` entirely
in the browser — no server involved.

## Files

- **model-data-rgb-only.json** — the model used by default for a live photo
  upload (`RiceML.predictFromCanvas`). Trained on 18 RGB/HSV/GLCM-texture
  features only, no NIR. **83.13% test accuracy.**
- **model-data.json** — the full 32-feature RGB+Pseudo-NIR fusion model
  (`RiceML.predictFromCanvasFusion`). **85.74% test accuracy.** Needs a real
  paired Pseudo-NIR image, which only exists for the bundled dataset —
  see "Why RGB-only is the default" below.
- **rice-model.js** — loads whichever JSON above and re-implements, in
  plain JS, what `training_testing/predict_sample.py` does in Python: the
  same feature extraction (RGB/HSV stats, GLCM texture, +NIR/NDVI for the
  fusion model), the same `StandardScaler` transform, and the same
  Gradient Boosting math scikit-learn uses internally (900 or 900-ish
  small regression trees summed, softmax at the end) — not an
  approximation of the model, the same arithmetic.
- **README.md** (this file).

Both `.joblib` models live in `training_testing/` — regenerate their JSON
exports any time either is retrained by running
`training_testing/export_model_to_json.py`.

## Why RGB-only is the default (this used to be broken)

The fusion model needs a Pseudo-NIR band alongside the RGB photo. For the
training images that band already exists
(`training_testing/Preprocessed/Pseudo_NIR/`), generated by a
`Preprocessing.ipynb` that was **not included** in the delivered project —
so it can't be reproduced for a brand new uploaded photo.

An earlier version of this file tried anyway: it synthesized a fake NIR
band from the RGB photo with a hand-guessed formula, then fed that to the
fusion model. On a real test image
(`training_testing/Preprocessed/RGB/Bacterial Leaf Blight/Bacterial_Leaf_Blight_0007.jpg`,
ground truth: Bacterial Leaf Blight) that pipeline predicted **Healthy
Rice Leaf at 45.5%** — wrong. A batch validation across all 6 classes
confirmed it wasn't a one-off: **32.7% accuracy**, barely better than
guessing.

Two rounds of fixing this:

1. **Fit the synthesis formula to real data instead of guessing.** The
   project's own dataset has real RGB->Pseudo-NIR pairs, so a linear
   regression was fit against 288,000 sample pixels (R-squared = 0.957 vs.
   the true NIR values). That alone roughly doubled batch accuracy to
   64.0% (true-NIR ceiling on the same batch: 92.7%) — better, but a
   synthetic NIR that's a *linear function of R,G,B* can't carry any
   information that wasn't already in the RGB photo, so there's a hard
   ceiling no amount of formula-tuning can cross.

2. **Use a model that was never trained to need NIR in the first place.**
   The training notebook already evaluates exactly this ablation (see
   `evaluate_feature_subset` / `RGB_ONLY_IDX` in
   `Rice_Fusion_NDVI_Feature_Training.ipynb`) and reports **83.13% test
   accuracy** for an RGB-only Gradient Boosting model — it just never
   saved that model to disk. It's been reproduced here (same 70/15/15
   split, same `random_state=42`, same hyperparameters — verified to
   match the notebook's reported number to the decimal) and exported as
   `model-data-rgb-only.json`. On the Bacterial Leaf Blight test image
   above, this predicts **Bacterial Leaf Blight at 90.4%** — correct. On
   the same 42-image validation batch: **92.9%** accuracy.

**This is the model `predictFromCanvas` uses by default now.** The fusion
model is still available via `predictFromCanvasFusion(canvas, nirPixels)`
for anything that has a real paired NIR image (e.g. if a future feature
lets someone browse/re-run predictions on the bundled dataset, which does
ship with true Pseudo-NIR).

## Validation

All accuracy numbers above were checked by running the JS port and the
real Python/scikit-learn model on the same images and comparing outputs
directly (not just eyeballing predictions):

- Fusion model, given true NIR: **42/42** predictions matched Python
  exactly (probability differences ~1e-5 to 1e-2, floating-point noise
  only).
- RGB-only model reproduces the notebook's reported test accuracy
  (83.13%) to the decimal, using the identical train/val/test split.

There's no automated regression test wired into CI for any of this yet —
it was checked manually. Worth scripting if either model changes often.

## Remaining limitation

Both models were trained on tightly-cropped, single-leaf, mostly plain-
background 128x128 photos. A live upload gets resized/cropped to roughly
that shape before feature extraction (see the `inferCanvas` setup in
`js/upload.js` / `js/detection.js`), but a busy background, multiple
leaves, or a very different lighting/angle than the training photos will
still shift the color/texture statistics away from what the model learned
— that's a training-data domain-shift issue, not something fixable in
this JS layer.

## Out-of-distribution guard ("this doesn't look like a rice leaf")

The model was trained only on the 6 rice-leaf classes — it has no
"none of these" option, so without a guard it will always force a
confident-looking guess even on a photo of a person, a wall, or noise.

**This guard used to be broken.** The original version only used a
statistical outlier score (mean squared z-score of the scaled feature
vector) with a threshold calibrated against a handful of synthetic test
images (noise, gradients, solid colors). A real photo of a person wearing
a plaid shirt scored 2.4 on that metric — comfortably *inside* the
"looks like a leaf" range (threshold was 20) — and got confidently
misclassified as Sheath Blight. The z-score alone wasn't a reliable signal
for real photos; skin tones and patterned clothing can land inside the
statistical range the training photos occupy even though the image looks
nothing like a leaf.

**Fixed by adding a second, independent signal: vegetation-color
fraction.** `greenFraction()` measures what proportion of pixels have a
green channel not clearly dominated by red or blue (`g >= r - 5 && g >= b
- 5`). A photo is now accepted only if **both** signals agree it looks like
a leaf:

```js
looksLikeRiceLeaf = outlierScore < 20 && greenFraction >= 0.30
```

Calibration (checked directly, not assumed):
- **900 real dataset images** sampled evenly across all 6 classes,
  including heavily necrotic/discolored diseased leaves — green fraction
  ranged from **0.337 to 1.0**. Zero false rejections at the 0.30
  threshold.
- The **portrait test photo** that broke the old guard: green fraction
  **0.095**, correctly rejected.
- A flat solid-green test image (no leaf texture at all) has a green
  fraction of 1.0 but is still caught by the *original* z-score check
  (1485 — wildly outside the training range), so the two signals cover
  different failure modes rather than duplicating each other.

See `OUTLIER_THRESHOLD` and `GREEN_FRACTION_THRESHOLD` in `rice-model.js`
if either needs retuning for a wider variety of real-world uploads.
